  • Catalogo.jsx, DetalleProducto.jsx, Carrito.jsx
  • Pago.jsx (checkout) y payment/Payment.jsx (medios de pago)

  • App Android con Capacitor (carpeta android/)

Controlador — backend (8081 y 8082)

Java 21 con HttpServer, pool de al menos 32 hilos, ManejadorBase y 16 manejadores. WebSocket en el puerto 8082.

  • ManejadorBase: CORS, 1.200 peticiones por minuto por IP, cuerpo máximo de 5 MB, X-Correlation-ID e identidad desde el token firmado
  • ManejadorPagosWompi: intención y confirmación del pago
  • ManejadorPedidos, ManejadorProductos, ManejadorFactura
  • ManejadorSalud: /health/live y /health/ready

Modelo — dominio y persistencia (5432)

Entidades Java, 11 DAO con JDBC y PreparedStatement, y un pool de conexiones propio (Conexion.java, 24 por defecto; no usa HikariCP).

  • Entidades: Producto, Pedido, Usuario, RolloTextil, TransaccionWompi…
  • DAO: ProductoDAO, PedidoDAO, PagoWompiDAO, InventarioDAO…
  • PostgreSQL 17: 29 tablas, transacciones con setAutoCommit(false)

Flujo de compra en la tienda

Lo que hace hoy el checkout (servicioWompi.js → ManejadorPagosWompi → PagoWompiDAO).

1

Vista

Payment.jsx envía POST /api/pagos/intencion con los artículos, el cupón y los datos de envío.

2

Controlador

ManejadorBase aplica CORS, límite de peticiones y tamaño; el manejador revisa que no lleguen datos de tarjeta.

3

Modelo

crearIntencionPago abre la transacción, lee cada producto con FOR SHARE y recalcula el total.

4

PostgreSQL

Inserta el pedido pending y sus líneas con el precio congelado, y hace COMMIT.

5

Confirmación

POST /api/pagos/confirmar debería marcar el pedido paid y descontar el stock.

-- Intención de pago (simplificado de PagoWompiDAO.crearIntencionPago)
BEGIN;
  SELECT id, nombre, precio, stock, vendedor_id, activo FROM productos WHERE id = 1 FOR SHARE;
  INSERT INTO pedidos (usuario_id, ..., monto_total, estado, metodo_pago, estado_pago, referencia_pago, ...)
       VALUES (4, ..., 44750, 'pending', 'wompi', 'pending', 'DD-1794937755678-A74203FD', ...);
  INSERT INTO items_pedido (pedido_id, producto_id, cantidad, precio_por_metro, subtotal)
       VALUES (1, 1, 1.0, 25000, 25000);
COMMIT;

-- Aprobación (PagoWompiDAO.procesarTransaccionWompi)
BEGIN;
  SELECT id, estado, estado_pago, ... FROM pedidos WHERE referencia_pago = ? FOR UPDATE;
  UPDATE pedidos SET estado = 'paid', ... WHERE id = ?;
  UPDATE productos SET stock = GREATEST(0, stock - ?), actualizado_en = NOW() WHERE id = ?;
COMMIT;
Estado al 17/11/2026: la confirmación responde 400 porque el filtro PCI confunde la referencia DD-<13 dígitos>-XXXX con un número de tarjeta. El pedido queda pending y el stock no se descuenta. El endpoint POST /api/pedidos (PedidoDAO, con FOR UPDATE por producto) sí descuenta el stock, pero el checkout no lo usa.
